# Выполнение и восстановление публикации

Обязательная процедура для агента при сбое публикации. Её цель — сначала использовать существующие рабочие инструменты и установить фактическое состояние, затем исправлять подтверждённый дефект. Этот документ не разрешает публикацию, изменение прав доступа или обход ограничений: действуют согласованный scope и правила `AGENTS.md`.

## 1. Зафиксировать задачу и исполнителя

Прочитать последние указания пользователя, актуальный workflow и существующее состояние `.agent/tasks/active.json`. Зафиксировать версию, канал, commit скрипта, commit исходников релиза, активный run/job и владельца выполнения. Не запускать второй publisher параллельно первому. Не использовать грязную или старую локальную копию как доказательство поведения удалённого кандидата.

## 2. Восстановить рабочий способ

Найти последний успешный запуск того же канала и его фактическую команду. Проверить применимость к текущей версии и машине. Перечень названий инструментов не заменяет попытку подключения или API-запрос.

Подтверждённый исторический маршрут к отдельной Windows-ВМ: SSH к Proxmox, затем `qm guest exec 103`. Имя гостя — `BG3-MODIO`. Адрес хоста и имя настроенного ключа сверять по локальной конфигурации и предыдущему успешному подключению, не угадывать и не публиковать секреты. Для сложной PowerShell-команды использовать `-EncodedCommand`, сохраняя читаемый исходный текст в материалах задачи.

Если sandbox блокирует SSH/сеть, использовать предусмотренный запрос разрешения на конкретное подключение. Не обходить отказ через другой бинарник. Ошибка sandbox не доказывает недоступность ВМ. До действий проверить `qm status 103` и `hostname` внутри гостя; не проверять WinRM Windows-гостя по адресу Proxmox-хоста.

## 3. Получить фактические run, job и ошибку

Использовать GitHub connector или уже настроенный `gh`. Для connector проверять схему и фильтры текущего инструмента. PR-only выдача не отвечает на вопрос о push/dispatch.

Проверенный GET-маршрут коллекции запусков:

```text
https://api.github.com/repos/Underslumber/bg3-dnd55e-russian-localization/actions/runs?head_sha=<commit>&per_page=5
```

По ответу получить jobs и лог упавшего шага. Если фильтр не дал результата, проверить HTTP-ошибку, правильность SHA, коллекцию без фильтра и нужные страницы выдачи. Не просить пользователя искать ссылку на run, пока доступный API позволяет получить её самостоятельно.

Разделять завершённый failure, выполняющийся job, пустой результат фильтра и отсутствие доступа. После timeout сначала выяснить состояние уже запущенной операции; timeout не разрешает повторную загрузку.

## 4. Проверить ВМ до изменения кода

Для ошибки авторизации прочитать штатные hooks и проверить их результат на ВМ. Исторические пути: `C:\ProgramData\BG3Modio\PreJob-ToolkitAuth.ps1`, `PostJob-ToolkitAuth.ps1`, `Ensure-LarianBrowserSession.js`; текущие пути сверять с настройкой runner. Не печатать credentials, cookies, OAuth query/fragment или содержимое auth-файлов.

Проверять отдельно:

| Граница | Достаточное наблюдение | Недостаточное наблюдение |
|---|---|---|
| Larian | Аккаунт открыт в авторизованном состоянии | Наличие файла auth или процесса браузера |
| mod.io | Открывается файловый менеджер точного мода | Сообщение `Larian browser session ready` |
| Выбор вкладки | Фактические цели браузера и точный путь нужного мода | Требование одной вкладки на весь браузер |
| Загрузка | Новый modfile ID и версия | Нажата кнопка Publish |
| Публикация | Этот файл активен для нужной платформы | Успешен workflow или существует GitHub ZIP |

При signed-out состоянии осмотреть реальные видимые элементы выделенного браузера ВМ. В успешном восстановлении 24.09.2026 использовалась видимая кнопка `Log in with Larian Studios` на BG3-портале; существующая сессия Larian завершила OAuth и вернула браузер в файловый менеджер мода. HTML `BUTTON` может не иметь `href`: отсутствие URL у кнопки не означает отсутствия действия. Не подставлять придуманные маршруты вместо наблюдаемого действия; учитывать последние указания пользователя о способе входа.

Перед кликом проверить правильный сайт/контекст, видимость, доступность и однозначность кнопки. После клика проверить реальный переход и возврат к точному моду. CAPTCHA, MFA или реальный отказ доступа требуют соответствующего пользовательского действия; не обходить их. Не выходить из рабочей сессии только ради воспроизведения ошибки без согласования такого теста.

## 5. Контроль перед правкой или остановкой

В существующей записи задачи сохранить без секретов:

```ini
target = версия, канал, VM, commit скрипта и исходников
working_baseline = ссылка на успешный run и использованный способ
failed_boundary = конкретный слой и симптом
attempt = фактический вызов и его ответ
runtime_observation = что непосредственно увидено на целевой машине
rejected_hypothesis = какой вывод опровергнут и чем
next_action = доступный разрешённый шаг
user_only_requirement = конкретное недостающее действие пользователя либо none
```

Если `next_action` доступен и разрешён, выполнить его. Объяснение ошибки или ответ на статусный вопрос не завершает исходное поручение. Если пользователь прямо переключил задачу на расследование причины, выполнять расследование и не возобновлять публикацию без его указания.

Код менять только после связи наблюдаемого сбоя с конкретным дефектом текущего исполняемого скрипта. После двух неудачных попыток не продолжать подбор URL/селекторов: получить новое прямое наблюдение или независимый диагноз по действующим правилам субагентов. Передавать буквальное ТЗ и evidence, а не только собственное объяснение. Счётчик попыток сохраняется.

## 6. Завершить существующую операцию

Проверить файлы mod.io до повторной загрузки. Если файл уже есть, использовать предусмотренную финализацию вместо повторного upload. При поиске новых файлов учитывать порядок и пагинацию API; старейшая первая страница не доказывает отсутствие свежей версии.

Для повторного run прочитать его workflow и checkout refs. Закреплённый job можно повторить после восстановления сессии, если его код и исходники подходят задаче; неизменный SHA сам по себе не запрещает rerun. Если требуется другой код, старый запуск не доказывает его работу.

Запустить только согласованный канал, дождаться результата и независимо проверить ID, фактическую версию и активный статус файла. Указать ожидающие одобрения платформы отдельно. Не создавать новый тег/версию и не повторять успешные каналы ради восстановления mod.io.

Исторический проверяемый пример: [run 35877678387, attempt 2](https://github.com/Underslumber/bg3-dnd55e-russian-localization/actions/runs/35877678387/attempts/2) — файл `8244835`, версия `0.5.20.2`, Windows live. Это пример рабочего способа, не текущая версия релиза и не команда на его повторную публикацию.
